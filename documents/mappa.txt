UNIVERSUM — MAPPA TECNICA INTEGRALE DEL PROGETTO MODULARE
Data revisione: 22 novembre 2026
Versione: riorganizzazione strutturale mantenendo il gameplay dell’ultima release con le regole Firestore aggiornate.
====================================================================================================

A. ARCHITETTURA IN BREVE
----------------------------------------------------------------------------------------------------
Il repository ospitato su GitHub Pages contiene soltanto codice client statico. La progressione offline è salvata in IndexedDB; l’online usa Firebase Authentication e documenti Firestore, governati da firestore.rules pubblicate separatamente nella console Firebase.
Non sono introdotti Cloud Functions, pacchetti npm di produzione o un sistema di compilazione obbligatorio: ogni modulo è un semplice script JavaScript caricato da index.html con defer.
La modularizzazione è conservativa: non cambia formule, nomi delle API window.Universum*, formato salvataggi né regole Firestore. Le classiche API pubbliche rimangono in data.js, db.js, engine-core.js, galaxy.js, multiplayer.js e ui-core.js; le implementazioni sono suddivise sotto modules/.

B. COSA AVVIENE QUANDO APRI IL GIOCO
----------------------------------------------------------------------------------------------------
1) Il browser legge index.html e style.css; scarica gli SDK Firebase esterni (se raggiungibili).
2) Gli script locali defer vengono scaricati in parallelo, ma ESEGUITI nello stesso ordine dei tag in index.html prima di DOMContentLoaded.
3) modules/offline/storage.js apre l’accesso IndexedDB tramite db.js; modules/data/* registra i cataloghi ed espone UniversumData.
4) modules/engine/* crea Engine; engine-actions.js aggiunge le azioni. modules/galaxy/* crea la galassia offline; Firebase e modules/online/* preparano MP.
5) ui-core.js prepara UI.state e gli helper; modules/ui/* e ui-social.js/ui-guide.js registrano renderer; missions-core.js, siege-missions.js e tutorial.js attivano plugin.
6) Con DOMContentLoaded la lobby mostra gli universi locali. All’entrata offline UI.startGame carica uno stato esistente. Online UI.startOnlineGame gestisce listener e sync con Firestore.
7) UI.startGameLoop esegue tick simulativo periodico. Il rendering costoso è in parte sospeso in background, ma la progressione economica resta attiva. All’apertura di un salvataggio offline processOfflineProgress recupera il tempo trascorso.

C. STRUTTURA DEI DATI E DEI FLUSSI
----------------------------------------------------------------------------------------------------
OFFLINE: modules/offline/storage.js ↔ IndexedDB (universes, id); engine/actions ↔ universe.planets e researches; modules/galaxy/*.js ↔ galaxyDeltas/fleetsInFlight/messages; UI legge lo stato corrente e lo salva via UniversumDB.
ONLINE: modules/online/universes.js ↔ online_universes + players + planets; sync.js ↔ lastUpdated + inbox; fleet-control/combat-resolver.js ↔ fleets e pianeti; communications.js ↔ messages/chat/private_chats; bots.js ↔ pianeti BOT e Mercante.
SICUREZZA: Firestore verifica request.auth e regole del file. Non è presente un calcolatore autorevole di produzione e PvP lato server: un client alterato può ancora falsificare dati propri non verificati dalle regole.
ASSET: graphics-core, ships, structures generano illustrazioni Canvas; non sono sorgenti di regole economiche.
ESTENSIONI: missions-core registra una ricerca aggiuntiva dopo il caricamento base; siege-missions aggiunge tick assedi; tutorial.js opera solo offline.

G. CONTRATTI CHE NON DEVONO CAMBIARE IN FUTURI REFACTOR
----------------------------------------------------------------------------------------------------
1. Le API window.UniversumData, window.UniversumEngine, window.UniversumGalaxy, window.UniversumMP, window.UniversumDB, window.UniversumUI restano stabili per compatibilità con il codice esistente.
2. I registri privati window.__Universum*Modules servono come collegamento tra funzioni estratte. I bridge const nome = (...args) => G.nome(...args) risolvono le dipendenze tra moduli anche in presenza di cicli; non sostituiscono validazioni server.
3. Ogni file modules/* è una funzione anonima immediata (IIFE) in strict mode. index.html deve sempre caricare context prima delle implementazioni e il file API pubblico dopo.
4. Le chiavi di universe.planets, fleet, defenses, researches, galaxyDeltas e lastSeen sono salvate su IndexedDB: per cambiarle serve normalizzazione/migrazione in engine/foundation e offline/storage.
5. La versione schema flotte online (FLEET_SCHEMA_VERSION = 2) è in modules/online/context.js; cambiare formato richiede regole Firestore e migrazioni.
6. I plugin vengono caricati DOPO i motori e la UI perché estendono cataloghi/tick/API.
7. Non caricare legacy/engine.js: ridefinisce il motore e appartiene all’archivio storico.
8. Non introdurre nuove scritture Firestore senza aggiornare le rules e testare accessi con più account.

Non basta un test sintattico: dopo il deploy verificare nuova partita offline, partita esistente, edifici/ricerche, flotta, spionaggio, Mercante, tutorial, mobile, online con due account e update Firestore Rules.
PUBBLICAZIONE: copiare TUTTA la cartella universum-main su GitHub Pages; includere modules/ ed escludere browser-test temporanei. Su Firebase pubblicare separatamente il CONTENUTO di firestore.rules via Console (o CLI). Non fare deploy di regole vecchie.
PWA: dopo pubblicazione forzare refresh; installazioni precedenti possono trattenere cache finché la nuova versione del Service Worker non si attiva.
TEST REALI NON ESEGUITI QUI: Firebase Emulator/servizio live, stress CPU/GPU di dispositivi reali, compatibilità Safari mobile. I controlli automatici coprono la logica disponibile senza backend.
